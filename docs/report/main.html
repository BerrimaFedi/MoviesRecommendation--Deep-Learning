1. Introduction et rappel du projet

Le projet vise à recommander des films à des utilisateurs, y compris des films jamais notés (démarrage à froid). Chaque film est décrit par trois modalités : son affiche (image JPEG 342 px de large), son synopsis (texte anglais) et ses métadonnées (genres, langue, année, durée). Les notes proviennent de MovieLens ml-latest-small [23] ; le contenu, de l'API TMDB, avec le dataset Kaggle « The Movies Dataset » en secours. La Tâche 1 a fixé les sources et l'évaluation (RMSE, NDCG@K, Recall@K, test de démarrage à froid strict sur 5 % des films) ; la Tâche 2 a produit des scripts de collecte reprenables et un premier jeu préparé.

La Tâche 3 transforme ces scripts en un pipeline DataOps automatisé, testé, versionné et reproductible (partie A), dans l'esprit des pratiques MLOps [9], puis choisit et spécifie l'approche de fusion à implémenter (partie B), en s'appuyant sur les caractéristiques mesurées du jeu de données. 2. Architecture DataOps

2.1 Vue d'ensemble

Le pipeline est déclaré dans dvc.yaml [10] (figure 1) : seize étapes, chacune étant un module Python python -m src.<paquet>.<module> aux entrées et sorties explicites. Une seule commande, dvc repro, reconstruit les données prêtes pour le modèle à partir des sources ; DVC compare les empreintes du code, des données et des paramètres déclarés à celles de dvc.lock et ne relance que les étapes périmées. Nous l'avons vérifié : modifier preprocessing.text.min_len_chars invalide uniquement preprocess_text et son aval ; les ingestions, l'image et les notes restent en cache.

2.4 Étapes et données produites

Ingestion. Le code réseau de la Tâche 2 est conservé : limitation de débit, reprise sur 429/5xx, cache JSONL reprenable, validation Pillow des affiches. Trois améliorations ont été apportées. (i) Si le cache TMDB est complet et frais, l'étape ne fait aucun appel réseau et n'exige aucun identifiant, ce qui permet de rejouer le pipeline hors ligne. (ii) Le repli SSL non vérifié de la Tâche 2 a été supprimé. (iii) Nous avons corrigé un défaut révélé par la validation : le secours Kaggle demandait les affiches des 45 000 films Kaggle au lieu des seuls films du catalogue, et le manifeste contenait 35 507 entrées hors catalogue. Elles sont désormais filtrées, et un contrôle les signale ; python -m src.ingestion.posters --prune-orphans a supprimé les 4 761 affiches concernées (270,7 Mo), ramenant le manifeste à 9 692 entrées. Toutes les sorties d'ingestion sont déclarées persist pour que DVC n'efface jamais le cache reprenable.

Prétraitement par modalité (une étape chacune, sorties dans data/interim/) : catalog (genres MovieLens vers un vocabulaire canonique de 20 genres, année du titre, identifiant IMDb) ; text (Unicode NFC, suppression des caractères de contrôle, espaces normalisés, longueur minimale de 20 caractères, secours Kaggle) ; images (fichier présent, JPEG RGB décodable, côté ≥ 16 px, empreinte SHA-1) ; meta (langue ISO 639-1, durée 0 traitée comme inconnue, popularité TMDB seule) ; ratings (doublons, domaine). Alignement : jointure movie_id ↔ tmdb_id avec contrôle de cardinalité (many_to_one), union des genres MovieLens ∪ TMDB, et masques explicites (has_overview, has_poster, has_meta, modality_mask ∈ {TIM, T-M, …}). Aucun film n'est supprimé faute de modalité. Découpage : 5 % des films éligibles en démarrage à froid strict, puis découpage chronologique global 80/10/10 sans fuite.

Sur les données réelles, le pipeline reproduit exactement les tables de la Tâche 2 : mêmes 9 742 films, mêmes 100 836 notes, découpage identique note par note. Les seules différences sont trois colonnes ajoutées et deux synopsis dont un caractère invisible U+200B a été retiré par la normalisation.

2.6 Versionnement, CI et traçabilité

Données. dvc.lock fixe l'empreinte MD5 de chaque sortie ; git checkout task3 && dvc checkout restaure exactement les données de l'étiquette. Le remote par défaut est un dossier partagé (../dvc-storage-movies) ; un tiers le redéfinit localement (dvc remote modify --local shared url …, ou un remote Google Drive), puis lance dvc pull. Sans accès au remote, dvc repro reconstruit tout depuis les sources publiques (README, §3).

CI sans données réelles. MovieLens et TMDB interdisent la redistribution : on ne peut donc pas publier un extrait réel dans le dépôt. La CI exécute le DAG DVC complet en mode ingestion.mode: synthetic : src/ingestion/synthetic.py génère 120 films et 1 800 notes au format exact des sources (CSV MovieLens, JSONL TMDB, JPEG, CSV Kaggle). Ce jeu comporte des défauts réalistes (tmdbId absent, film inconnu de TMDB, synopsis vide, affiche manquante) et un vrai signal multimodal : le genre influe sur la couleur de l'affiche, le vocabulaire du synopsis et les notes. La configuration CI hérite de la configuration principale (extends) et écrit dans data_sample/. Le générateur refuse d'écraser de vraies données (test dédié).

Traçabilité et bonus. Le rapport reports/quality_report.html, généré automatiquement, contient le tableau de bord des étapes, tous les contrôles, les distributions et la dérive. La fiche de données reports/data_card.md (sources, licences, volumes, biais, prétraitements) est régénérée à chaque exécution. La détection de dérive s'appuie sur reports/profile.json, qui contient des histogrammes à bornes fixes ; le PSI se calcule par rapport à une référence figée ou à une étiquette Git (python -m src.reporting.drift --ref-rev task3). Un test vérifie qu'un décalage de la durée et de l'année déclenche une alerte. S'y ajoutent une collecte planifiée (workflow mensuel, qui rafraîchit aussi le cache TMDB avant l'échéance des 6 mois) et un Dockerfile.

2.7 Données apportées par un tiers et découpage figé

Un tiers (enseignant, binôme) peut déposer ses propres données dans le dossier versionné inbox/ : movies.csv (nouveaux films : titre, année, genres, synopsis, langue, durée, affiche), ratings.csv (notes sur des films MovieLens ou nouveaux, d'utilisateurs existants ou nouveaux) et posters/. L'étape ingest_external est une porte de qualité dédiée. Elle contrôle colonnes et encodage UTF-8, identifiants entiers sans collision avec MovieLens, film référencé connu, note dans le domaine, horodatage lisible et non futur, durée et année plausibles, codes de langue, affiche présente et décodable (ré-encodée en JPEG RGB). Les films valides suivent ensuite exactement le même chemin que les autres (alignement, masques, représentations), avec une provenance source = external visible dans le tableau de bord. En démonstration, python -m src.ingestion.external --example dépose 2 films, 5 notes et 2 affiches, et dvc repro ne relance que ingest_external et l'aval : les deux films sont complets (masque « TIM ») et reçoivent leurs représentations. Avec --example-bad (collision d'identifiant, affiche absente, note à 7 étoiles, film inconnu), le pipeline s'arrête à ingest_external en nommant les quatre défauts.

Évaluation stable. Recalculer le découpage à chaque arrivée de données déplacerait les bornes chronologiques et le tirage des films froids : les métriques ne seraient plus comparables. Le découpage est donc figé dans configs/split_spec.json, versionné par Git (bornes, liste des 182 films froids, sources couvertes). Les notes des sources non couvertes vont dans un segment new, ni appris ni évalué. Nous l'avons vérifié : le découpage figé reproduit exactement celui de la Tâche 2, et l'ajout de l'exemple ne modifie l'affectation d'aucune des 100 836 notes MovieLens. Deux contrôles de validate_processed vérifient la conformité à la spécification. Re-geler (python -m src.splitting.freeze) intègre les nouvelles données à l'apprentissage : c'est une décision explicite, tracée par un commit, typiquement prise quand le tableau de bord signale une dérive.

4. Choix argumenté de l'approche

Le choix découle des mesures du tableau 1 et du profil des données, et non de considérations générales.

CritèreCe que montrent nos donnéesConséquence pour la fusion
Nature des modalitésTrois modalités de granularité très différente : une image de 342×513, un texte court (médiane 43 mots, p95 87, max 176) et un vecteur tabulaire de 42 dimensions (20 genres multi-hot, 17 catégories de langue one-hot, année et durée standardisées, indicateurs de manque). Une seule observation par film et par modalité.Chaque modalité se résume bien en un vecteur global. Les synopsis tiennent dans la fenêtre de 256 jetons de MiniLM, donc sans troncature. Encodeurs propres à chaque modalité, puis projection dans un espace commun : fusion intermédiaire.
AlignementAppariement exact échantillon par échantillon par la clé tmdb_id (contrôlé par validate_processed) ; aucune séquence temporelle à synchroniser entre modalités.Pas d'alignement explicite à apprendre : les mécanismes faits pour des séquences non alignées (MulT, attention croisée jeton à jeton, goulots MBT) ne servent pas ici.
Interactions inter-modalesChaque modalité suffit en partie : le genre est porté à la fois par les métadonnées, le synopsis et le style de l'affiche (Jaccard MovieLens/TMDB 0,71 : l'information de genre est redondante et bruitée). L'utilité vient surtout de la complémentarité, et la modalité la plus fiable varie selon le film.Il faut une pondération apprise par film plutôt que des interactions multiplicatives d'ordre élevé (TFN, MCB). La porte de la GMU répond exactement à ce besoin.
Modalités manquantesPeu de manques de contenu (99,0 % de films complets ; 48 sans affiche, 46 sans aucun contenu). En revanche, il manque une composante essentielle : les 182 films froids n'ont aucune note d'entraînement, et 15,7 % des notes val/test portent sur un film absent du train.Traiter l'identifiant collaboratif comme une 4ᵉ modalité, absente pour les films froids (principe de DropoutNet) ; porte masquée, jetons « absent » appris, modality dropout.
Volume de données77 048 notes d'entraînement, 7 690 films et 523 utilisateurs vus en train ; médiane de 3 notes par film. C'est bien trop peu pour affiner un ResNet ou un BERT de bout en bout.Encodeurs pré-entraînés figés (ResNet-50 / CLIP, Sentence-BERT), représentations mises en cache par extract_features ; seuls la projection, la fusion et les tours sont entraînés (≈ 3,8 M de paramètres, dont 2 M d'embeddings d'identifiants).
Ressources de calculGTX 1650 Max-Q (4 Go) ; un lot de 256 notes passe sur CPU en quelques millisecondes une fois les représentations en cache.Un entraînement complet se mesure en minutes, ce qui permet les ablations et les baselines prévues. L'attention complète reste possible, mais en ablation seulement.
InterprétabilitéLe projet doit montrer l'apport de chaque modalité, surtout en démarrage à froid.Les poids de porte z donnent la contribution par modalité et par film ; elle est complétée par des ablations (retrait d'une modalité à l'évaluation).
Décision. Nous retenons une fusion intermédiaire par unité multimodale à porte (GMU) généralisée à quatre voies et masquée : texte, image, métadonnées et identifiant collaboratif. Elle s'appuie sur des encodeurs pré-entraînés figés et ajoute deux pertes auxiliaires : des têtes unimodales contre le déséquilibre entre modalités, et un alignement contrastif texte ↔ image. Nous écartons la fusion précoce, qui gère mal les absences et mélange des échelles hétérogènes, et la fusion tardive, qui ne peut pas exploiter l'identifiant quand il existe tout en s'en passant pour les films froids. TFN, LMF et MCB sont écartés faute d'interactions d'ordre élevé utiles sur des vecteurs globaux redondants, et les transformers multimodaux faute de séquences à aligner et de volume. La concaténation et l'attention entre modalités-jetons restent comme baselines et ablations.

Point de vigilance relevé par les mesures. Seules 9,4 % des notes de validation et de test viennent d'un utilisateur présent en train : le découpage chronologique global de la Tâche 1 place la plupart des utilisateurs récents hors du train. Un embedding d'identifiant utilisateur ne suffit donc pas. La tour utilisateur proposée (§5.1) construit aussi l'utilisateur à partir de son historique antérieur (moyenne des représentations des films qu'il a déjà notés, en respectant la chronologie). Nous évaluerons en complément un découpage chronologique par utilisateur, à décider avec l'encadrant.

5.2 Description formelle du module de fusion

Soit M = 4 modalités, xm la représentation figée de la modalité m et μm ∈ {0,1} son masque de présence (has_overview, has_poster, has_meta, identifiant connu).

pm = LN(Wpm · LN(xm)) ∈ ℝd ,   p̃m = μm pm + (1 − μm) am

hm = tanh(Wm p̃m) ,   s = Wz[p̃1; … ; p̃M] ∈ ℝM×d ,   sm,k ← −∞ si μm = 0

zm,k = exp(sm,k) / Σm' exp(sm',k) ,   h = Σm zm ⊙ hm ,   e = LN(Wo h + bo)

Ici am est un jeton « absent » appris. La porte est un softmax par dimension k sur les modalités, ce qui généralise z ⊙ hv + (1 − z) ⊙ ht de la GMU à deux voies [4]. Le masque −∞ garantit qu'une modalité absente ne vote pas (zm = 0, vérifié par un test). Si toutes les modalités sont absentes (46 films), le masque est levé et e ne dépend plus que des jetons appris : le modèle prédit alors à partir des biais, comme une baseline de popularité. La contribution de la modalité m est cm = moyennei,k zm,k(i), avec Σm cm = 1.

5.3 Fonction de perte

L = (1/|B|) Σ(u,i) (ŷui − yui)²  +  λuni · Luni  +  λcon · LInfoNCE

  • Têtes unimodales : ŷ(m)ui = μ + bu + ⟨u, pm⟩ et Luni = Σm μm(ŷ(m) − y)² / Σm μm. Chaque modalité doit être prédictive à elle seule, ce qui contrecarre la domination de l'identifiant collaboratif, plus facile à exploiter sur les films très notés. C'est une version simple de la supervision par modalité [17]. λuni = 0,3.
  • Alignement contrastif : InfoNCE symétrique (type CLIP [8]) entre ptexte et pimage des films du lot qui ont les deux modalités, avec τ = 0,07 et λcon = 0,1. Elle rapproche les deux vues d'un même film dans l'espace commun, ce qui stabilise les projections entraînées sur peu de données.
  • En Tâche 4, pour le classement (NDCG@10), nous testerons aussi une perte BPR à échantillonnage négatif en complément de la MSE.

5.4 Modalités manquantes et déséquilibre

  • Absence explicite : les masques produits par le pipeline (mask dans items.npz) alimentent la porte. On n'impute jamais une modalité absente par des zéros.
  • Modality dropout (p = 0,3 par modalité de contenu) à l'entraînement seulement, ce qui rend le modèle robuste aux absences [21] et limite la co-adaptation.
  • Id dropout (p = 0,5) : l'identifiant d'un film d'entraînement est masqué une fois sur deux, si bien que le modèle apprend à scorer à partir du seul contenu. C'est la situation exacte des 182 films froids, dont l'indice vaut toujours 0 (vérifié sur un vrai batch).
  • Déséquilibre : les têtes unimodales et le dropout ci-dessus. Si les contributions cm restent très déséquilibrées, nous appliquerons une modulation de gradient de type OGM-GE [18].

5.5 Pseudo-algorithme (passe avant et entraînement)

Entrées : cache {x_texte ∈ ℝ^384, x_image ∈ ℝ^2048, x_meta ∈ ℝ^42, masque μ ∈ {0,1}^3} par film,
          notes d'entraînement (u, i, y), indices : idx(i) = 0 si i ∉ train
Paramètres : projections P_m, embeddings E_item, E_user, jetons absents a_m, GMU F, biais

pour chaque époque, pour chaque lot B = {(u, i, y)} :
 1. p_t ← P_t(x_texte[i]) ; p_v ← P_v(x_image[i]) ; p_g ← P_g(x_meta[i]) ; p_id ← E_item[idx(i)]   # (|B|, 4, 256)
 2. μ ← [μ_texte, μ_image, μ_meta, idx(i) > 0]
 3. μ[:, :3] ← μ[:, :3] · Bernoulli(1 − 0,3) ; μ[:, 3] ← μ[:, 3] · Bernoulli(1 − 0,5)        # entraînement seul
 4. p̃_m ← μ_m · p_m + (1 − μ_m) · a_m
 5. e, z ← F(p̃, μ)                       # porte softmax masquée, e ∈ ℝ^(|B|×256)
 6. ŷ ← μ_global + b_u + w_b·e + ⟨E_user[u], e⟩ ;  ŷ^(m) ← μ_global + b_u + ⟨E_user[u], p_m⟩
 7. L ← MSE(ŷ, y) + 0,3 · Σ_m μ_m (ŷ^(m) − y)² / Σ μ + 0,1 · InfoNCE(p_t, p_v | μ_t = μ_v = 1)
 8. rétropropagation, AdamW (lr 1e-3, weight decay 1e-4), écrêtage du gradient à 1
 fin ; sélection du modèle sur la RMSE de val ; journalisation MLflow (paramètres, commit, empreinte des données)

Inférence film froid : idx(i) = 0 ⇒ μ_id = 0 ⇒ z_id = 0 ; e dépend du seul contenu.

Prototype implémenté (bonus). src/fusion/ contient la GMU masquée, la concaténation et l'attention entre modalités-jetons, le modèle à deux tours, les pertes et le pont avec le pipeline (RatingBatches). python -m src.fusion.smoke exécute une passe avant et une rétropropagation sur un vrai batch de 256 notes issu de data/features/items.npz et data/processed/ratings.parquet. Dimensions obtenues : score (256), unimodal (256, 4), e (256, 256), z (256, 4, 256) ; 3,82 M de paramètres (GMU), 2,77 M (concaténation), 2,97 M (attention). Sur un lot de films froids, tous les indices valent 0 et la contribution mesurée de l'identifiant est exactement 0. Les sept tests de tests/test_fusion.py vérifient dimensions, masquage, cas tout-absent, gradients, dropout limité à l'entraînement, InfoNCE et la passe sur batch réel. Les représentations utilisées ici sont celles du backend light (sac de mots haché, vignette 16×16) ; le backend pretrained (ResNet-50, MiniLM) est déjà codé dans extract_features pour la Tâche 4.

5.7 Protocole d'évaluation

  • Métriques : RMSE (et MAE) sur les notes ; NDCG@10 et Recall@10 en classement (pertinent : note ≥ 4), calculés par utilisateur. Le tout est rapporté séparément sur test (films vus), cold_item_test (films jamais vus) et, au sein de test, sur les utilisateurs vus et non vus (user_in_train).
  • Ablations : (a) retrait d'une modalité à l'évaluation (masque forcé à 0), sans réentraînement puis avec ; (b) remplacement du module de fusion (GMU → concaténation → attention) ; (c) suppression des pertes auxiliaires (λuni = 0, λcon = 0) et de l'id dropout, dont l'effet attendu porte surtout sur cold_item_test ; (d) encodeurs light vs pretrained.
  • Rigueur : 3 graines par configuration, moyenne ± écart-type, intervalle de confiance bootstrap (par utilisateur) sur la différence avec la meilleure baseline ; hyperparamètres choisis sur val uniquement ; contributions cm rapportées par sous-ensemble.
